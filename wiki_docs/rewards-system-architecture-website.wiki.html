01 · Executive Summary

문서의 목적과 읽는 방법

이 페이지는 기술 구성도를 업무 관점에서 해석한 자료입니다. 개발자에게는 구조 확인용, PM/운영자에게는 영향도와 체크포인트 확인용으로 사용할 수 있습니다.

네트워크

VPC 내부를 Public/Private로 분리

Public subnet에는 외부 진입점에 가까운 NLB가, Private subnet에는 Docker Swarm 클러스터와 내부 리소스가 위치하는 구조로 볼 수 있습니다.

연동

기존 운영 환경과 함께 사용

MariaDB, NFS, API 서비스 등 기존 운영 자원은 별도 박스로 표시되어 있으며 S2S VPN으로 신규 영역과 연결됩니다.

06 · PM / 운영 체크리스트

오픈 전 확인해야 할 것

단순 인프라 구성 확인을 넘어, 실제 운영 전 검증해야 할 업무 체크포인트입니다.

네트워크/보안

WAF → NLB → Docker Swarm → 기존 운영 환경까지 통신이 실제로 가능한지, 방화벽/시큐리티그룹/라우팅을 함께 확인합니다.

특히 S2S VPN 구간은 터널 상태뿐 아니라 실제 API/DB/NFS 접속 테스트까지 해야 합니다.

도메인/인증서

www, api, membership, portal 도메인이 동일 인증서 범위에 포함되는지, WAF/NLB 매핑이 맞는지 확인합니다.

인증서 만료일, DNS TTL, 롤백용 기존 레코드 값을 사전에 정리해두면 장애 대응이 쉬워집니다.

모니터링

NLB 대상 상태, 컨테이너 replica, CPU/Memory, 디스크, 네트워크, VPN 상태를 대시보드로 묶어 확인합니다.

배포

ECR 이미지 태그 기준으로 배포 버전을 관리하고, 배포 전후 Smoke Test URL을 고정합니다.

백업

Snapshot은 생성 여부보다 복구 가능 여부가 중요합니다. 정기 복구 리허설 일정을 잡는 것이 좋습니다.

주의

단일 AZ 구성 여부

슬라이드상 Public/Private subnet 모두 ap-northeast-2a로 표기되어 있습니다. 고가용성 요구가 있다면 다중 AZ 구성 여부를 별도 확인해야 합니다.

주의

기존 운영 환경 의존성

MariaDB, NFS, API 서비스가 기존 운영 환경에 있으므로 VPN/방화벽/기존 서버 장애가 신규 리워즈 서비스에도 영향을 줄 수 있습니다.

확인

NFS 장애 영향도

업로드/정적 파일/공유 파일이 NFS에 의존한다면 장애 시 어떤 화면과 기능이 영향을 받는지 사전 정의가 필요합니다.

확인

Swarm Manager Quorum

Manager 노드 3대 구성은 일반적으로 quorum 관점에서 의미가 있으므로, #1~#3의 장애 조합별 영향도와 복구 절차를 정리해야 합니다.

VPC

AWS 안에 만든 사설 네트워크 공간입니다. 회사 전산실의 네트워크 구역을 클라우드에 만든 것으로 이해하면 됩니다.

Subnet

VPC 안을 목적별로 나눈 작은 네트워크입니다. Public은 외부 접점, Private은 내부 서버 구역으로 많이 사용합니다.

WAF

웹 공격을 막는 보안 필터입니다. SQL Injection, 비정상 요청, 특정 IP 차단 등에 사용합니다.

NLB

Network Load Balancer입니다. 들어온 요청을 여러 서버로 나눠 보내는 입구 역할입니다.

Docker Swarm

여러 서버 위에서 컨테이너 서비스를 묶어 운영하는 클러스터 기능입니다.

S2S VPN

Site-to-Site VPN입니다. 신규 AWS 네트워크와 기존 운영망을 사설망처럼 연결하는 방식입니다.
