1. 비개발자용 개요

이 문서는 “관리자 화면에서 바꾸는 정책”이 아니라 “코드에 직접 입력되어 운영되는 정책”을 모아둔 자료입니다.

핵심

왜 중요한가?

호텔, 바우처, 결제, 이벤트 팝업이 코드에 있으면 간단한 운영 변경도 개발 수정과 배포가 필요합니다.

PM 관점

무엇을 확인해야 하나?

변경 요청을 받을 때 “관리자 수정 가능/개발 수정 필요”를 먼저 구분해야 일정과 리스크를 정확히 잡을 수 있습니다.

운영 방향

어디로 개선해야 하나?

반복 변경되는 항목은 관리자화해서 운영자가 직접 수정하고, 코드는 정책 엔진만 담당하는 구조가 좋습니다.

3. 운영자 매뉴얼 버전

현업 요청이 들어왔을 때, 아래 순서로 판단하면 됩니다.

1. 요청 접수
현업 요청이 문구 변경인지, 노출 조건 변경인지, 특정 호텔/상품/바우처 정책 변경인지 구분합니다.
2. 하드코딩 여부 확인
관리자 메뉴에서 수정 가능한지 먼저 확인하고, 관리자 항목이 없으면 이 문서의 위치 파일을 기준으로 개발 수정 대상으로 분류합니다.
3. 변경 대상 정리
호텔 ID, 상품 ID, 바우처 ID, URL, 이미지 파일, 다국어 키, 적용 기간, 최소 금액을 표로 정리합니다.
4. 개발 요청
수정 파일 경로와 변경 전/후 정책을 함께 전달합니다. 바우처는 개발 ID/운영 ID를 반드시 분리합니다.
5. 검수
개발/스테이지에서 조건별 노출·비노출, 링크 이동, 다국어 문구, 모바일 화면을 확인합니다.
6. 운영 배포 후 확인
운영 환경에서 실제 호텔/상품/바우처 기준으로 최종 확인하고 변경 이력을 남깁니다.

9. 변경 시 주의사항

하드코딩 정책 변경은 단순 텍스트 수정이 아니라 서비스 노출 조건을 바꾸는 작업입니다.

RISK

운영 정책이 코드에 있음

호텔, 바우처, 결제, 이벤트 팝업 같은 업무 정책이 관리자 화면이 아니라 코드 파일에 박혀 있어 변경 시 개발 배포가 필요합니다.

RISK

운영/개발 ID가 다름

바우처 ID가 개발·운영 환경별로 다르게 정의되어 있어, 요청서에서 환경을 명확히 구분해야 합니다.

RISK

다국어 키와 이미지가 분리 관리됨

화면 문구는 다국어 키, 이미지는 public 폴더, 링크는 상수 파일에 있어 한 번의 콘텐츠 변경도 여러 파일 점검이 필요합니다.

RISK

이벤트/기간 정책은 만료 리스크 있음

이벤트 팝업, 제주 공사기간, Season Exclusive 기간처럼 날짜가 지나면 화면 정책이 어긋날 수 있습니다.

RISK

상품/호텔 코드 변경 영향 큼

hotelCode, prodID, diningId, hotelId가 URL·필터·예약 이동에 직접 쓰이므로 오입력 시 잘못된 상품/호텔로 연결됩니다.

RISK

관리자 부재로 운영 대응 속도 저하

간단한 문구·링크·기간 수정도 개발자 확인, 코드 수정, 배포 절차가 필요해 운영 유연성이 낮습니다.
