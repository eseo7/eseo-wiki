01 · 비개발자용 개요

이 문서는 “통합회원” 기능을 연결하는 API 사용 설명서입니다.

무엇을 위한 문서인가?

IC, Rewards, 더파르나스의 회원 계정을 조회·가입·통합·수정·동기화하기 위한 API 목록과 입출력 항목을 정리한 문서입니다.

PM은 무엇을 봐야 하나?

API 코드 전체보다 “어느 화면/업무에서 어떤 API가 호출되는지”, “필수값이 무엇인지”, “실패 시 어떤 에러가 나는지”를 확인하는 것이 중요합니다.

핵심 리스크

회원 통합은 이름, 전화번호, 이메일, 멤버십번호 같은 식별값에 의존합니다. 값이 틀리면 다른 계정과 매핑되거나 통합 상태가 꼬일 수 있습니다.

03 · 운영자 매뉴얼 버전

운영자가 실제로 볼 때는 이 순서로 확인하면 됩니다.

STEP 1문의 유형 확인

로그인 실패, 회원통합, 신규가입, 정보수정, 비밀번호, 탈퇴, CMS 동기화 중 어느 유형인지 먼저 분류합니다.

STEP 2회원 식별값 확보

loginId, webMemberId, rewardsMembershipId, membershipNo, 휴대전화, 이메일 등 확인 가능한 값을 정리합니다.

STEP 3관련 API 선택

조회는 MI-REWARDS-022, 통합은 002, 가입은 006, 정보 수정은 007/008, 동기화는 014~018을 우선 확인합니다.

STEP 4결과와 에러 확인

resultCode, msg, data 값을 확인하고 실패 시 ERROR 시트의 코드 의미와 원인을 함께 확인합니다.

05 · PM/기획자 체크리스트

개발 코드보다 먼저 확인해야 할 항목입니다.

화면/업무와 API가 매칭되는가?

로그인, 통합, 가입, 수정, 탈퇴, 동기화 중 어떤 화면에서 호출되는 API인지 확인합니다.

회원 식별값이 명확한가?

webMemberId, rewardsMembershipId, loginId, membershipNo, cmsProfileId 등 기준값을 혼동하지 않습니다.

필수값(Y)이 누락되지 않았는가?

요청 항목에서 Mandatory가 Y인 값은 화면/관리자/배치에서 반드시 전달되어야 합니다.

통합상태 W/R/U와 통합유형 U/T/N을 구분했는가?

회원 타입과 통합 판단값은 의미가 다르므로 테스트케이스에서 별도 확인합니다.

개발/운영 URL을 혼동하지 않았는가?

운영 반영 요청 시 Base URL과 호출 방향을 반드시 확인합니다.

에러코드 대응 문구가 준비되어 있는가?

실패 시 고객/운영자에게 보여줄 안내 문구와 내부 처리 기준이 있어야 합니다.

CMS/CRS 동기화 범위가 명확한가?

회원정보 변경 후 어느 시스템까지 동기화되어야 하는지 확인합니다.

개인정보/비밀번호 항목 처리 기준이 있는가?

패스워드, CI, 전화번호, 이메일 같은 민감 정보는 로그/화면 노출 기준을 별도로 확인합니다.

09 · 용어 설명

처음 보는 사람이 헷갈리기 쉬운 용어

API

화면이나 시스템이 필요한 데이터를 주고받기 위해 호출하는 통신 규격입니다.

Request

API를 호출할 때 보내는 값입니다. 필수값이 빠지면 실패합니다.

Response

API 호출 후 시스템이 돌려주는 결과값입니다. 성공/실패와 회원 데이터가 포함됩니다.

W/R/U

회원 타입입니다. W는 IC 웹회원, R은 Rewards 회원, U는 통합회원입니다.

U/T/N

통합 판단 유형입니다. U는 통합대상, T는 전환대상, N은 미대상입니다.

CMS/CRS

더파르나스와 예약/멤버십 시스템 쪽 회원 정보를 주고받는 외부 연동 대상입니다.

Mandatory

필수 여부입니다. Y로 표시된 항목은 요청 시 반드시 전달되어야 합니다.

Direction

어느 시스템에서 어느 시스템으로 호출되는지 나타냅니다.

resultCode

API 처리 결과 코드입니다. 일반적으로 성공은 1000으로 표시됩니다.
