1. 비개발자용 개요

이 문서를 처음 보는 사람을 위한 설명

무엇을 하는 업무?

잘못 적립된 포인트를 되돌리는 업무

객실 체크아웃, 식음 결제 등으로 적립된 포인트가 취소되어야 할 때 DB 프로시저 또는 보정 쿼리로 포인트를 0 처리하거나 잔액에서 차감합니다.

왜 중요함?

정산 마감 전에 맞춰야 함

운영 포인트 취소 건은 정산 마감일 이전에 처리되어야 월별 포인트 정산 데이터가 어긋나지 않습니다.

가장 조심할 점

식음은 구매 데이터가 2개일 수 있음

식음 포인트는 tb_membership_user_purchase_info가 2개 생기는 케이스가 있어 일반 취소 프로시저로 처리되지 않을 수 있습니다.

2. 문서 전체 내용 분석 요약

원문 개발 문서를 업무 관점으로 재정리

핵심 결론

  • 일반적인 객실 포인트 취소는 SP_MANUAL_POINT_CANCEL_PROC 프로시저를 먼저 호출합니다.
  • 프로시저 호출 후에는 반드시 결과를 확인해야 합니다.
  • 식음 포인트는 POS 데이터 구조 때문에 취소가 안 되는 경우가 있으며, 이때는 purchase ID 기준으로 직접 보정합니다.
  • 강제 포인트 취소는 숙박 실적 valid_nights와 적립 포인트 point를 함께 조정합니다.

PM이 이해해야 할 포인트

  • 취소 요청에는 주문번호, 멤버십 번호, 취소 사유, Jira/요청 근거가 필요합니다.
  • 객실인지 식음인지 먼저 구분해야 처리 방식이 달라집니다.
  • 식음 여부는 개발 기준으로 platform_type = POS 여부를 확인합니다.
  • 월말 정산 전에 처리하지 못하면 다음 정산에 영향을 줄 수 있습니다.

3. 운영자 매뉴얼 버전

개발 언어를 줄이고 실제 업무 순서로 설명

취소 요청 접수

고객/현업/정산 담당자로부터 포인트 취소 요청이 오면 주문번호, 멤버십 번호, 발생일, 취소 사유, 관련 Jira 또는 요청 메일을 확보합니다.

포인트 유형 구분

객실 예약으로 생긴 포인트인지, 현장 식음 결제로 생긴 포인트인지 확인합니다. 식음 포인트는 POS 데이터 때문에 별도 확인이 필요합니다.

기본 취소 프로시저 먼저 실행

일반 케이스는 개발자가 주문번호와 요청자를 넣어 기본 취소 프로시저를 실행합니다. 실행 후 취소 결과를 반드시 확인합니다.

식음 예외 케이스 확인

식음 포인트 취소가 실패하면 purchase ID가 2개 생긴 케이스인지 확인합니다. 이 경우 ID가 더 큰 구매 데이터를 기준으로 직접 보정할 수 있습니다.

정산 마감 영향 확인

정산 마감일 이전에 취소가 완료되었는지 확인합니다. 적립일이 다음 달 1일이면 다음 달 말일까지 처리 기준이 달라질 수 있습니다.

처리 결과 공유

취소 완료 후 포인트 잔액, 적립 내역, 전표 내역, 정산 반영 여부를 확인하고 요청자에게 완료 결과를 공유합니다.

5. PM/기획자 체크리스트

개발자가 아닌 사람이 꼭 확인할 항목

Jira, 메일, 운영 요청서 등 취소 사유가 남아 있어야 합니다.
예: 2511079703, 2505127718 등 주문번호 오입력 시 다른 포인트가 변경될 수 있습니다.
식음은 platform_type = POS 여부와 purchase 데이터 중복 여부를 확인해야 합니다.
호출만으로 끝내지 말고 실제 포인트/잔액/전표가 바뀌었는지 확인해야 합니다.
모든 운영 포인트 취소는 말일 정산 전까지 처리되는 것이 원칙입니다.
처리일, 처리 방식, 확인 결과, 예외 여부를 남겨야 추후 정산 이슈 대응이 쉽습니다.

6. 개발자 복사센터

코드, URL, SQL을 바로 복사할 수 있게 정리

각 코드 블록은 선택 복사도 가능하고, 우측 복사 버튼으로 전체 복사할 수 있습니다. 실제 운영 적용 전에는 반드시 대상 주문번호·회원·구매ID를 검증해야 합니다.
기본 포인트 취소 프로시저복사 가능한 원문
CALL SP_MANUAL_POINT_CANCEL_PROC('2511079703', 'PM', 'https://h2ohospitality.atlassian.net/browse/PAR-1209');
식음 포인트 취소 - 변수 확인복사 가능한 원문
# 취소 되지 않은 주문인 것 직접 확인 후 id 값이 더 큰 purchase id 입력
set @purchaseId = 453;
set @userId = (select membership_user_info_id from tb_membership_user_purchase_info where id = @purchaseId);
set @accId = (select id from tb_membership_user_point_acc_info where membership_user_purchase_info_id = @purchaseId);
set @cancelPoint = (select point from tb_membership_user_point_acc_info where membership_user_purchase_info_id = @purchaseId);
set @expireDate = (select CONCAT(YEAR(DATE_ADD(insert_date, INTERVAL 5 YEAR)), '1231') from tb_membership_user_point_acc_info where membership_user_purchase_info_id = @purchaseId);

select @purchaseId, @userId, @accId, @cancelPoint, @expireDate;
식음 포인트 취소 - 적립/잔액/전표 보정복사 가능한 원문
-- 포인트 취소 처리
UPDATE tb_membership_user_point_acc_info
SET `point` = 0,
    update_user = 77777777,
    update_date = NOW()
WHERE membership_user_purchase_info_id = @purchaseId;

-- 신규 테이블 포인트 정보 수정 (적립 날짜 기준으로, 5년 뒤의 것이 유효한 point)
UPDATE tb_membership_user_point_info
SET balance_point = balance_point - @cancelPoint,
    update_user = 77777777,
    update_date = NOW()
WHERE membership_user_info_id = @userId
  and expired_date = @expireDate;

-- 신규 테이블 전표 포인트 금액 취소 처리
UPDATE tb_membership_user_point_slip_info
SET balance_point = 0
WHERE membership_user_purchase_info_id = @purchaseId;
강제 포인트 취소복사 가능한 원문
// 예약 실적에 해당하는 숙박 일수를 차감
UPDATE tb_membership_performance_info
SET valid_nights = 0
WHERE order_number = '2505127718';

// 적립됐던 포인트 차감
UPDATE tb_membership_user_point_acc_info
SET point = 0
WHERE membership_user_purchase_info_id = (
    SELECT tb_membership_performance_info.membership_user_purchase_info_id
    FROM tb_membership_performance_info
    WHERE order_number = '2505127718'
);

7. 상세 업무 정리

업무 유형별 처리 기준

기본 취소

객실 포인트 취소

객실로 받은 포인트는 기본적으로 SP_MANUAL_POINT_CANCEL_PROC 프로시저로 취소 처리합니다. 주문번호, 요청자, 사유 URL을 넣어 호출합니다.

예외 케이스

식음 포인트 취소

식음 포인트는 POS 영수증 데이터 때문에 구매 정보가 2건으로 생성될 수 있습니다. 이 경우 ID가 더 큰 purchase ID를 기준으로 직접 보정하는 흐름이 필요합니다.

주의 필요

강제 포인트 취소

예약 실적의 숙박 일수와 적립 포인트를 직접 0 처리합니다. 정산과 회원 실적에 영향이 있으므로 사전 검증과 승인 근거가 필요합니다.

식음 포인트 취소 시 확인해야 하는 데이터

확인 항목의미PM 관점 체크
platform_type = POS식음 포인트 여부 판단 기준식음 취소 요청인지 먼저 확인
membership_user_purchase_info_id구매 데이터 ID식음은 2개일 수 있어 대상 ID 확인 필요
tb_membership_user_point_acc_info포인트 적립 내역point가 0 처리되었는지 확인
tb_membership_user_point_info회원별 포인트 잔액balance_point에서 취소 포인트가 차감되었는지 확인
tb_membership_user_point_slip_info포인트 전표/스냅샷전표 금액도 0 처리되었는지 확인

8. 주의사항

운영 사고를 막기 위한 핵심 경고

1) 프로시저 호출 후 결과 확인 필수

문서에서도 “일단 프로시저부터 호출하고 결과를 꼭 확인해야 함”이라고 되어 있습니다. 호출 성공과 실제 데이터 반영은 별개로 봐야 합니다.

2) 식음 포인트는 예외가 많음

식음 포인트는 구매 데이터가 2건으로 쌓여 일반 취소가 실패할 수 있습니다. 이 경우 직접 SQL 보정이 필요할 수 있습니다.

3) 정산 마감일 이전 처리

모든 운영 포인트 취소 건은 정산 마감일, 즉 말일 이전에 처리해야 합니다. 단, 적립일이 다음 달 1일이면 다음 달 말일까지 처리 기준으로 볼 수 있습니다.

4) 강제 취소는 영향 범위 확인

강제 취소는 숙박 실적과 적립 포인트를 직접 수정합니다. 정산, 회원 등급, 실적 산정에 영향을 줄 수 있어 처리 근거와 검증이 필요합니다.

9. 용어 설명

개발 용어를 업무 언어로 쉽게 해석

프로시저DB 안에 저장된 처리 프로그램입니다. 여기서는 포인트 취소 처리를 자동으로 수행하는 명령 묶음입니다.
purchaseId구매 데이터의 내부 ID입니다. 식음 포인트 예외 처리 시 어떤 구매 건을 취소할지 결정하는 핵심 값입니다.
point해당 구매 건으로 적립된 포인트 금액입니다. 취소 시 0으로 바꿉니다.
balance_point회원이 보유한 포인트 잔액입니다. 적립 취소 시 기존 잔액에서 취소 포인트만큼 차감합니다.
slip_info포인트 전표/스냅샷 내역입니다. 회계나 정산 관점에서 포인트 이동 기록을 확인하는 데이터입니다.
POS식음 현장 결제 시스템입니다. 식음 포인트는 POS 영수증 데이터와 연결됩니다.
정산 마감월별 포인트 적립/사용/취소 내역을 회계 데이터와 맞추는 기준 시점입니다.
Jira Ticket작업 사유와 요청 근거를 남기는 이슈 관리 번호입니다. 포인트 취소 사유로 사용됩니다.
valid_nights숙박 실적 일수입니다. 강제 취소 시 실적도 함께 조정될 수 있습니다.
